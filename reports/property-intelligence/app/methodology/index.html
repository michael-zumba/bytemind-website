1. What this project is — and what it is not

Auckland Property Scout is an independent, non-commercial research project covering 17 suburbs on Auckland's North Shore and Eastern Bays: Browns Bay, Murrays Bay, Mairangi Bay, Rothesay Bay, Campbells Bay, Castor Bay, Milford, Long Bay, Waiake, Torbay, Takapuna, Devonport, Mission Bay, Kohimarama, St Heliers, Glendowie and Ōrākei.

It has one main job: make the evidence behind a property estimate visible. Instead of a single confident-looking price, it shows a reasonable range, where that range came from, when it was observed, and how wrong the model has been on comparable cases.

What it is

  • A dated snapshot of public listing information and derived research signals.
  • A set of ranges and indicators that can be inspected, tested and reproduced.
  • A record of what changed over time: asking prices, sale method, listing copy, and whether a listing left the market.
  • A public release of derived data, schema and code so another person can audit or rebuild the work.

What it is not

  • Not a valuation. It is not a valuation under professional standards and cannot replace a registered valuer.
  • Not a sale-price prediction. The main model target is a third-party automated valuation, not a future sale price.
  • Not financial, legal or tax advice. Decisions about a property need title checks, a builder's report, legal advice and, where required, a registered valuation.
  • Not a live market feed. It refreshes daily, but every figure is a snapshot with a timestamp. Listing pages can change between captures.
The shortest accurate description: a transparent, error-aware property research instrument. It helps a reader ask better questions. It does not answer “what will this sell for?” with certainty.

2. The data: what is collected and when

The daily collector reads public Trade Me residential sale search results and listing pages for the 17 target suburbs. It stores the listing facts needed for research, plus a timestamp for every capture.

What is captured

Refresh and retention

  • The automation runs daily at 03:15 local time, with a slower browser fallback if the public site blocks a request.
  • Every capture is timestamped. Recent snapshot history is kept in full; older snapshots are compacted to the first and last capture per listing per month to keep the database bounded.
  • Listings that disappear from a complete 17-suburb search are kept and marked delisted with a date. If they return, they are marked relisted. Their descriptions, prices and model outputs remain in the record.
  • Raw source descriptions are retained privately for reproducibility. They are not redistributed in the public release because they are third-party page content.

Listing universe and cleaning

The public counts and medians use standard residential listings that are currently active. Non-standard entries such as relocatable homes, tiny homes, rentals and other unusual listings are excluded by default but can be revealed with a toggle. Leasehold properties are kept but flagged, because comparing a leasehold price with a freehold estimate would be misleading. Tenure is inferred from listing text, not from the title record.

At the 28 October 2026 snapshot the database contains just over 1,000 captured listings, of which about 1,000 are active and standard. Those counts change every day; the app displays the current figures.

3. The price shown on the map and in the listings

There are two different ideas in property data that are easy to confuse:

  • Asking price — what the vendor or agent currently advertises.
  • Value estimate — a model's or valuer's opinion of what the property may be worth.

The map and the listing cards now use the same rule so they cannot disagree:

Displayed price ruleeffective price = asking price, if it exists
otherwise: estimate midpoint → comparable midpoint → value-guide midpoint

“Otherwise” is shown with a tilde, for example ~$1.40m. The tilde means “this is a value guide, because there is no asking price.” A plain $1.02m means the listing itself is asking that amount. The same rule is applied to the map bubble, the listing card, the price filter and the price sort.

Worked example. A property is advertised at $1,023,000. The map used to show a $1.4m AVM in the bubble; that was a different quantity. Under the current rule the bubble and card both show $1.02m (money is rounded for the map). If the same property were offered by auction with no asking price, the bubble would show ~$1.40m and the legend would identify it as a guide.

Why both prices are still useful: the asking price tells you what the vendor is trying to achieve. The value guide tells you what the evidence suggests. The app shows the asking price on the map and keeps the estimate range in the listing detail, so neither is hidden.

4. How a value range is built

The project uses a hierarchy. It does not blend every signal into one black box. Each signal is presented with its source and confidence, and the next method is used only when the earlier one is unavailable or unreliable.

Step 1 — Find the advertised signal

The listing page is read for an asking price, a guide (“enquiries over”), an auction date or a deadline. This tells the model how the vendor is asking buyers to respond. It is not treated as a valuation.

Step 2 — Use the Homes.co.nz AVM when it exists

Homes.co.nz publishes an automated valuation model (AVM) range for many properties. The project uses its low, middle and high estimate, plus the date it was updated, as the primary published range when it is available. The AVM is an independent estimate — a useful one — but it is still a model output, not a sale price.

Step 3 — Build a range from nearby sold comparables

When there is no AVM, the project looks for recent nearby sales of a similar property type. It converts each sale into a ratio to that property's council CV, then applies the subject property's CV. This puts a small unit and a large house on a more comparable footing.

Comparable-sales calculation weightᵢ = exp(−distanceᵢ / 1.4) × exp(−ageᵢ / 11) × type_weightᵢ × same_suburb_factorᵢ
ratioᵢ = sale_priceᵢ / CVᵢ
range = [Q25(ratio) × CV_subject, Q50(ratio) × CV_subject, Q75(ratio) × CV_subject]

In plain language: a sale 0.5 km away and a few months old counts more than a sale 2 km away and two years old. The 1.4 km and 11-month numbers are the decay scales used by the model; they are not a claim that distance or time stop mattering at exactly those points. The type weight gives more influence to the same property type and less to a very different one. A same-suburb sale gets a small extra weight. Q25, Q50 and Q75 are weighted quartiles: the low, middle and high points of the comparable evidence.

Worked example. Suppose the subject property has a CV of $1,200,000. The weighted comparables produce ratios whose 25th, 50th and 75th percentiles are 0.82, 0.90 and 1.01. The displayed range is roughly:

Worked examplelow = 0.82 × $1,200,000 = $984,000
mid = 0.90 × $1,200,000 = $1,080,000
high = 1.01 × $1,200,000 = $1,212,000

The range is not a confidence interval in the statistical sense. It is a summary of the spread of the comparable evidence. If there are only two or three usable sales, the range is labelled lower confidence and should be treated more cautiously.

Step 4 — Use a calibrated hedonic fallback when needed

A hedonic model estimates a property from its characteristics. The project trains one on listings that have a Homes AVM, then uses it only when neither an AVM nor usable comparables are available and the confidence is acceptable.

Hedonic model (simplified)log(estimate_mid) = β₀ + β₁·log(CV) + β₂·beds + β₃·baths + β₄·parking
+ β₅·log(land) + β₆·log(floor) + … + suburb + type + tenure + error

In plain language: the model learns how much each characteristic is associated with a higher or lower AVM, after allowing for the others. Taking logs makes percentage differences easier to model and keeps predictions positive. The model is trained and tested on different folds of the data so its error is measured on cases it did not see.

Step 5 — Keep the council CV as a cross-check, never as market value

The council capital value is an official rating value. It is usually updated on a multi-year cycle, so it lags the market. It is used as a feature, a denominator for comparable ratios and a sanity check — not as a current market estimate.

Which range wins?

  1. Homes AVM, when available.
  2. Comparable-sales range, when usable sales exist.
  3. Calibrated hedonic range, only when confidence is medium/high.
  4. Active-suburb guide as a last resort, clearly labelled as the weakest signal.

The detail payload also carries every available signal and a methodology note, so a reader can see what was used rather than only the final range.

5. Error, confidence and validation

A range is only useful if its error is measured. The project reports three standard quantities.

Error measuresMAE = average(|prediction − reference|)
MAPE = average(|prediction − reference| ÷ reference) × 100%
R² = share of variation in the reference explained by the model

MAE is the average dollar miss. MAPE turns that miss into a percentage, which is easier to compare across cheap and expensive properties. R² runs from 0 to 1; higher means the model tracks the reference more closely, but it says nothing about whether the reference itself is right.

Worked example. If a model predicts $1.08m and the reference is $1.00m, the absolute error is $80,000 and the absolute percentage error is 8%. A model with a 7% MAPE is therefore typically about $70,000 off on a $1.0m property — useful for research, not precise enough to treat as a valuation.

The 80% interval is built from the model's out-of-fold errors. It means that, on the validation sample, about 80% of actual values fell inside the stated interval. It is a calibration check, not a guarantee for a particular property.

Two cautions matter. First, the with-CV model is accurate partly because both the AVM and the CV are closely related. Second, the validation is random 5-fold cross-validation, not a time-based backtest. Daily snapshots will make a genuine temporal test possible later; until then the error figures should be read as internal validation, not an external audit.

6. Sale method and motivation pressure

Sale method is stored on a rough six-step ladder:

StageMethodInterpretation
0AuctionVendor is testing the market and may accept a pre-auction offer.
1TenderBuyers submit offers by a deadline.
2Deadline saleSimilar to tender, with a stated deadline.
3Price by negotiationNo public number; a range may be discussed.
4Price guide / enquiries overA public expectation, often expressed as a floor.
5Asking priceAn explicit advertised number.

The 0–100 sale-pressure score is a bounded motivation proxy, not a prediction:

Sale-pressure scorescore = 50 × (stage / 5)
+ 30 × min(days_on_market, 180) / 180
+ min(20, 8 × price_drops + 10 × method_changes)

In plain language: half the score reflects how explicit the vendor's price signal is, 30% reflects how long the property has been listed, and up to 20 points reflect observed price reductions or method changes in the last 180 days. A score of 40–64 is labelled medium and 65+ high. The weights are a transparent heuristic, not estimated from outcomes.

A cross-sectional test found no statistically significant stage coefficient after controlling for suburb, type, size and other factors. That is why the app calls this a motivation or urgency proxy, not a price predictor. With enough daily price and method changes, it will be possible to test within-listing transitions rather than only differences between listings.

7. Description, topics and text signals

Listing descriptions are public marketing copy. The project tests whether the way an agent writes carries information about price after controlling for the property and the location. It does not treat adjectives as facts.

Cleaning

Descriptions are normalised, stripped of HTML and contact details, and cleaned of cross-listing boilerplate such as agency names, viewing logistics, tender dates and repeated developer copy. Target suburb names are redacted before topic modelling so that “Milford” or “St Heliers” cannot become a topic that simply duplicates location.

Topics

TF-IDF converts words and two-word phrases into weighted counts; NMF (non-negative matrix factorisation) groups co-occurring terms into 12 topics. Each listing receives a topic share that sums to one. A listing can be partly about family living, partly about renovation, and so on.

Topic sharesW = topic weights from NMF (non-negative)
shareᵢ = Wᵢ / ΣW

NMF is a way of finding recurring mixtures of words without being told the topics in advance. The labels are editorial summaries; the top terms in the Research Lab are the authoritative description of each topic.

Lexicon signals

A small set of pre-specified word groups scores urgency, luxury, renovation/condition, views/waterfront, family/schools and investment language. These scores are descriptive. They are not added to the primary value range.

What the tests found

  • Adding text features improved a no-CV structural model in cross-validation, but adding text to the full model with CV made it slightly worse.
  • After Benjamini–Hochberg false-discovery-rate correction across the tested features, no individual topic or lexicon survived at 5% for the AVM/CV premium or the advertised-price gap.
  • The honest conclusion is a null result for individual text effects in this snapshot. Topic shares remain an exploratory signal and a way to compare copy over time, not a valuation input.
Why report a null result? Because a research project is more useful when it says what did not work. Marketing language is correlated with price in raw comparisons, but after location, size, type and method are controlled for, it does not reliably explain the premium in this sample.

8. Dated price changes and vendor behaviour

From the 28 October 2026 build, every listing has a dated asking-price history. The unit is a distinct observed price state, not a row for every day.

What is recorded

  • first_observed — the first price state seen for that listing.
  • price_change — a genuine movement from one number to another.
  • price_set — a listing moves from no asking price (auction, tender, POA) to a number.
  • price_removed — a number is withdrawn in favour of a no-price campaign.
  • price_display_change — the wording changes without a numeric move, such as “enquiries over” to “asking”.
  • description_change — the marketing copy changes between captures; the event stores a digest and character counts, not the private full text.

For each row the project stores the observed date, price, display text, sale method, previous price, dollar change, percentage change and days since the previous observation.

Change calculationschange = new_price − old_price
change_percent = change / old_price × 100%
days_between = date(new observation) − date(previous observation)

Worked example. A St Heliers listing was first observed at $1,690,000 on 23 October 2026. On 28 October it was $1,550,000. The change is −$140,000, or −8.3%, over 4.34 days. That is a fact about what was observed. It is not yet evidence that the property will sell at $1.55m.

The per-listing summary adds the useful aggregates: number of price changes, days to first change, average days between changes, cumulative change, largest drop and last direction. This is the raw material for later questions such as whether reductions cluster at particular listing ages, whether a description edit precedes a price cut, and how quickly vendors respond to a slow campaign.

Early sample warning: the current snapshot has only a few days of daily price-change history. The observed counts and medians are real, but they are far too small for a reliable general estimate of how fast Auckland vendors move. The document marks this as a growing panel, not a completed study.

9. Reproducibility and downloads

The project is designed so that another person can check the work rather than trust the interface.

  • The SQLite schema is public, including price history, events, model predictions and text tables.
  • The public release contains the compact database, schema, selected CSV extracts, analysis code, the release manifest and SHA-256 checksums.
  • A verification command checks the manifest, file hashes, SQLite integrity and row counts.
  • Raw third-party listing descriptions and photos are kept out of the public release. Derived features, metrics and code remain available, and the scraper is included so the source data can be collected independently.

10. Limitations and honest claims

  • The main target is an AVM, not a sale price. A model can track Homes.co.nz well without being a good predictor of what a property will sell for.
  • The sample is selected. Homes AVM matches ordinary houses more often than new builds, units and unusual titles. The fallback is therefore trained on a non-random subset and applied elsewhere; confidence labels reflect that.
  • Validation is not a temporal backtest. Random folds test internal generalisation. A true time-based test needs a longer daily panel.
  • Comparable ranges can be thin. Nearby sales are a limited public sample, not a complete sales register. Two or three sales can produce a range that looks more precise than the evidence supports.
  • CV is a lagging anchor. Council values are updated periodically and are not a current market price.
  • Tenure is inferred from words. Leasehold and cross-lease flags come from listing text; the title and ground rent must be checked directly.
  • Price history is young. The first reliable changes were captured in late October 2026. Early medians will move as the panel grows.
  • Text effects are null after correction. Topics and lexicon scores are exploratory, not causal price premiums.
  • No causation, no forecast. The project reports associations and observed behaviour. It does not claim that a particular feature causes a price, or that a price will move in a particular direction.

Where a number is uncertain, the interface should say so through a range, a confidence label, a source date or a caveat. If it does not, treat that as a defect to report, not as a stronger claim.

11. Glossary

Asking price
The number a vendor or agent currently advertises. It is a negotiating position, not a sale price.
AVM
Automated valuation model. A statistical estimate produced by a data provider, in this project primarily Homes.co.nz.
CV
Council capital value. An official rating value, updated periodically and used here as a cross-check and for comparable normalisation.
Comparable sale
A nearby sold property used as evidence for a subject property. In this project it is weighted by distance, recency, type and same-suburb match.
Hedonic model
A model that estimates a value from property characteristics such as size, bedrooms, location and CV.
MAE
Mean absolute error: the average dollar miss between predictions and reference values.
MAPE
Mean absolute percentage error: the average miss as a percentage of the reference value.
R²
The share of variation in the reference that a model explains. It is not a measure of whether the reference is correct.
80% interval
A range intended to contain about 80% of validation outcomes. Its coverage is checked empirically.
NMF
Non-negative matrix factorisation. A method for finding recurring mixtures of words in a document collection.
BH-FDR
Benjamini–Hochberg false discovery rate. A correction for testing many hypotheses at once; it makes it harder for a lucky result to look significant.
DOM
Days on market: how long a listing has been publicly advertised.
Price state
A distinct observed combination of asking price/display and sale method. Repeated daily captures of the same state do not create duplicate rows.
Delisted
A listing absent from a complete 17-suburb search. It is retained in the database with a date rather than deleted.
